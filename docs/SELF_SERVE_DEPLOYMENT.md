# Self-serve community setup: deployment design gate

**Status (11 Nov 2026): draft implementation under review; no deployment factory exists.** The hosted site must not accept a new community's treasury funds until all steps below pass on testnet. PR #14 keeps DAO creation closed.

## Why the current wallet flow stops

The existing Firewall's `new` method accepts initialization only when the caller is its own account. This protects an empty deployed contract from a third party choosing its DAO or verifier. A transaction signed by a council wallet and addressed to the new Firewall has that wallet as predecessor, so it cannot call `new`. A DAO proposal has the DAO as predecessor and cannot call `new` either. A browser cannot assume a wallet can sign as a newly created child account just because its public key was used there; wallet modules differ in account discovery and signing permissions.

## Required onchain setup path

1. Deploy and verify **one** reviewed Veyntro setup factory on testnet. The platform may provision this shared factory once; it must not hold or sign for any community's treasury. The factory's deployed code, account, version and source build hash must be public.
2. A new group creates or connects its own SputnikDAO with its own council policy. The hosted app reads the final DAO code and policy. Do not assume a wallet is a member from its name alone.
3. The group approves a DAO proposal to call the setup factory with its chosen verifier account and the exact required setup deposit. The factory requires the **DAO itself** as predecessor. It derives a unique child Firewall account from the DAO identity rather than trusting an arbitrary requested destination. A council wallet alone cannot create an instance for somebody else's DAO.
4. The factory creates the child account, transfers only the approved setup amount, deploys **pinned reviewed Firewall bytes**, and initializes with that DAO and verifier. This requires a narrowly scoped factory-compatible initializer in the new Firewall build; the existing self-only `new` behavior must remain safe for existing deployments. No user-supplied WASM or mutable contract URL may be deployed. No full-access key or unrestricted factory upgrade authority should be installed on the child.
5. The app waits for all relevant receipts, then re-reads the child and DAO at finality: exact approved code hash, DAO/verifier pairing, initialized state, and balance/backing. If an asynchronous step fails, show the actual final state and provide a reviewed recovery or refund path. Never say "ready" merely because the proposal was Approved or the first transaction succeeded.
6. The verifier must be a distinct community-controlled account with a scoped `submit_attestation` access key and an evidence policy tied to that specific Firewall. A reusable platform verifier key for all communities is not an acceptable shortcut. The group must be able to install or rotate its own restricted key without disclosing its private half to Veyntro.
7. Only after the DAO, Firewall and evidence checker are verified should the app expose governance funding and commitments. The group receives a public, wallet-free URL and can invite more council members under its DAO policy.

## Before enabling any signed setup action

- Determine and show the real testnet deposit and storage cost; the original 7 NEAR factory deposit was chosen funding, **not a measured minimum**. Confirm sufficient spendable funds and explain the DAO proposal bond separately.
- The draft factory now exposes `required_deposit({"operating_reserve":"..."})` at finality and rejects a deployment below that floor. It backs the compiled Firewall code plus 32 KiB of initial-state and growth headroom at the network's current storage price, then adds the selected operating reserve. This is a conservative funding requirement, **not a fee paid to Veyntro** and not a live measured deployment price. The DAO owns the child account and its balance. The original Firewall used 224,094 bytes of storage, including 219,974 bytes of code, at the Nov 11 check; its storage backing was about 2.24 testnet NEAR. The new compiled build may differ. Read the factory's live quote and check the DAO's balance and proposal bond before enabling a signing button.
- Contract CI run `43086132981` built a 225,379-byte Firewall with SHA-256 `04e7dc5ffaa8cfe9d58879641724ad0ec2a2608fdd426a22922a92201143b66a` and a 381,281-byte factory with SHA-256 `ebda5e982baa31026a0acc545e8c383c64dbd5030773586b63162e163cc94c10`. At the observed testnet storage price of 0.00001 NEAR per byte, the compiled child's floor with a 0.05 NEAR reserve would be **2.63147 testnet NEAR**. The one-time factory account separately needs enough balance to back its own code and state. These are build artifacts and an estimate, not deployed accounts or a live factory quote.
- The draft chooser accepts a factory child only when its code hash matches this pinned Firewall build, its deterministic address and final status match the factory's views, and the factory's own deployed code hash matches the pinned build. The existing Firewall path retains its original exact-code check. Rebuilds that change either WASM require a reviewed hash update before users may select new children.
- `/setup` can read the reviewed factory's code, derived child address, required starting deposit and setup/refund status from a single final testnet block. It cannot quote a nonexistent or different-code factory. A draft wallet path can create a DAO, request a DAO vote to deploy its child, and cast a vote after rechecking the exact receiver, verifier, amount, gas and final proposal. A final factory status and pinned code check distinguishes a finished child from a vote. All signed setup actions require `VITE_ENABLE_COMMUNITY_SETUP=true` in a dedicated test build; the public build leaves them closed. No deployed factory, live setup request or new child has been observed. Do not set that flag on public hosting yet.
- The draft `/verify` page calculates the exact canonical GitHub policy hash before the DAO proposes a commitment. For a commitment with that approved hash, it reads one final block, checks a real public GitHub Actions run against the exact repository, SHA, workflow, event and branch, and prepares the same evidence digest as the existing restricted verifier. The selected community verifier wallet alone signs `submit_attestation`; the page rechecks GitHub and chain state and confirms final recorded evidence. Its checks match the existing verifier's historical policy and unsigned payload in tests. This is a **manual community-controlled wallet path**, not a claim that the browser's validation is enforced by the contract or that every new group has restricted-key automation. The verifier remains trusted, the wallet key stays with the community, and a malicious verifier could sign outside the site. A real second-DAO browser transaction, wallet compatibility, recovery after redirect, independent review and automation/key-scoping decisions remain open.
- `python3 scripts/factory-preflight.py` is a read-only operator check for the one-time platform deployment. After rebuilding both WASMs from the reviewed commit, it refuses a byte mismatch with CI, checks the factory and parent accounts at finality, reads the current storage price, and prints separate factory-account and child starting-backing floors. It never signs, creates an account, or reads a key. Do not use the cost figures as permission to deploy before the remaining review and full setup flow are ready.
- Decide and test account-name collision, duplicate submissions, wallet redirect recovery, promise failure after account creation, and recovery of funds from partial setup.
- A failed atomic create/deploy/init batch records a refund attempt. Only after the refund completes does the DAO become eligible to retry setup; a pending or claimable refund cannot be bypassed. This has a unit test but still needs a real failed testnet receipt and proof that the funds returned before the flow is offered on the site.
- Test authorization attacks: another wallet using the same DAO name, forged DAO policy views, unapproved code, foreign verifier, factory reentry, and cross-community account selection.
- Run Rust tests, a final-block testnet deployment and an end-to-end browser setup with a fresh community wallet. Capture transaction and receipt IDs. Regression-check the original community.

`againa.testnet` should use this hosted flow as a normal group founder after it is complete. Its account existence and balance do not prove key control, DAO ownership or a usable Veyntro instance.
